# Дизайн: экспорт, импорт, прослеживаемость и защита данных

Дата: 2026-11-23. Статус: черновик, ждёт одобрения. Код не писался.
Основание: ответ пользователя по D1 («разобрать экспорт/импорт подробно, нужна прослеживаемость, нельзя удалять всё, нужен полный экспорт/импорт и полный сброс»), D2 («tuning игнорировать с предупреждением»), сводка аналитика AUD-001 (N-01…N-22), план M2.

## 1. Требования

1. **Прослеживаемость действий в сервисе.** Любое значимое действие (создание, завершение, переоткрытие, правка, смена ветки, удаление, восстановление, импорт, экспорт, сброс, резервное копирование, восстановление из копии) оставляет запись в журнале: когда, что, сколько, с каким результатом, откуда (UI / импорт / система).
2. **Нельзя случайно удалить всё.** Ни один частичный файл, ни одна ошибочная операция не должны молча стирать данные. Разрушительные операции — только явным режимом, с подтверждением, резервной копией и записью в журнал.
3. **Полный экспорт и импорт.** Полный снимок всех данных + формат + версия схемы. Полный импорт — отдельный явный режим «заменить всё».
4. **Полный сброс к дефолту.** Отдельный явный режим, с подтверждением, резервной копией и записью в журнал.
5. **Совместимость.** Импорт принимает текущие файлы `alpha-v0.3` / schema 3 и новый формат. Старые файлы не ломают приложение.

## 2. Текущее состояние (факты)

### 2.1 Хранилища
IndexedDB `livenotepad`, версия 1, четыре store:
- `notes` (keyPath `id`),
- `word_evidence` (keyPath `['stem','branch']`),
- `word_meta` (keyPath `stem`),
- `training_log` (keyPath `id`, autoIncrement).

### 2.2 Журнал
Типы событий в коде: `CREATE`, `COMPLETE`, `REOPEN`, `CORRECT`, `DELETE`, `RESTORE`, `EDIT`.
Чего нет: `IMPORT`, `EXPORT`, `RESET`, `BACKUP`, `RESTORE_BACKUP`; счётчиков, источника, результата, хэша файла, режима. `id` лога — autoIncrement, при импорте снимается и перенумеровывается: ссылки на лог нестабильны.

### 2.3 Экспорт
- `exportAll`: `version: 'alpha-v0.3'`, `schemaVersion: 3`, `exportedAt`, `tuning`, `notes`, `word_evidence`, `word_meta`, `training_log`.
- `exportNotes`: `version`, `schemaVersion`, `exportedAt`, `count`, `notes` — частичный файл.
- `exportLearning`: evidence + meta (проверить точный набор ключей).
- `exportLogs`: ключ `logs`, а импорт читает `training_log` — несовместимость.
- Манифеста секций, `exportId`, контрольной суммы нет.
- Событие `EXPORT` не пишется.

### 2.4 Импорт
`importAll`:
1. `JSON.parse` в try/catch.
2. Два `confirm` по `version` / `schemaVersion`.
3. Общий `confirm` по количеству.
4. `await DB.clearAll()` — **до** структурной проверки.
5. Последовательные `await DB.put*` в цикле — каждый в своей транзакции.
6. Ошибка в середине → `catch` → toast, часть данных уже применена, часть стёрта.

Следствия: `{notes:"x"}` проходит до цикла по символам; любой битый элемент после `clearAll` оставляет базу пустой или частичной; частичный файл стирает отсутствующие разделы (`exportNotes` — сам по себе путь к потере обучения и логов).

### 2.5 Сброс
`resetToDefault`: `confirm` → `DB.clearAll()` → 5 seed-заметок через `addNote`. Резервной копии нет, события `RESET` нет.

### 2.6 Монитор
Вкладка «Логи» фильтрует по типу; список типов захардкожен. Новые типы (`IMPORT`, `EXPORT`, `RESET`) не отображаются, пока список не расширен.

## 4. Принципы

1. **Сначала читать, потом писать.** Валидация и разбор файла не трогают БД.
2. **Одна операция — одна транзакция.** Никаких `await` внутри цикла заполнения.
3. **Частичный файл не удаляет.** Upsert по ключам, отсутствующие разделы не трогаются.
4. **«Заменить всё» — только явно.** Отдельная кнопка/режим, отдельное подтверждение, резервная копия.
5. **Любая разрушительная операция оставляет копию.** Перед импортом-заменой и сбросом — снимок в `backup`.
6. **Журнал append-only.** События не редактируются и не удаляются поштучно; чистятся только полным сбросом (с бэкапом).
7. **Стабильный идентификатор события.** `eventId` (UUID) сохраняется при экспорте/импорте, чтобы журнал не двоился и не терялся.

## 5. Модель данных (schema 4)

### 5.1 `training_log` → единый журнал действий
Store сохраняет имя `training_log` (совместимость, меньше миграции), но трактуется как журнал действий. Новые поля:
- `eventId` — UUID, стабильный;
- `ts` — число;
- `type` — `CREATE|COMPLETE|REOPEN|CORRECT|DELETE|RESTORE|EDIT|IMPORT|EXPORT|RESET|BACKUP|RESTORE_BACKUP`;
- `source` — `ui|import|system`;
- `result` — `ok|error`;
- `counts` — `{notes, evidence, meta, logs}` для операций с данными;
- `mode` — `merge|replace|full|partial` (для импорта/экспорта);
- `fileHash` — SHA-256 файла (если есть);
- `backupId` — ссылка на копию (для разрушительных операций);
- `details` — короткая строка/объект для диагностики.
Старые записи без `eventId` считаются `legacy`; при экспорте им присваивается детерминированный `eventId` (хеш от `ts|type|noteId|text`), чтобы повторный импорт не двоил.

### 5.2 `backup` (новый store, schema 4)
`{ id (autoIncrement), ts, reason, mode, counts, schemaVersion, data: {notes, word_evidence, word_meta, training_log} }`.
Политика хранения: последние 3 копии (настраиваемо в `TUNING`), при переполнении удаляется самая старая. Копии не экспортируются в `exportAll` по умолчанию (чтобы не раздувать файл); отдельная кнопка «экспортировать копию».

### 5.3 Заметка: обязательные поля и типы
`id` — непустая строка, уникальная; `text` — непустая строка; `createdAt` — конечное число; `completedAt`, `reopenedAt`, `dueAt`, `deletedAt` — `number|null`; `branch` — строка (включая `''`); `branchSource` — строка; `branchConfidence`, `dueConfidence` — число; `correctionCount` — число; `schemaVersion` — число.

## 6. Экспорт (формат 4)

```json
{
  "format": "livenotepad-export",
  "formatVersion": 4,
  "schemaVersion": 4,
  "appVersion": "alpha-v0.3",
  "exportedAt": "2026-11-23T...",
  "exportId": "uuid",
  "mode": "full|partial",
  "sections": { "notes": true, "word_evidence": true, "word_meta": true, "training_log": true },
  "counts": { "notes": 5, "word_evidence": 12, "word_meta": 3, "training_log": 40 },
  "checksum": "sha256:...",
  "tuning": { ... },
  "data": {
    "notes": [],
    "word_evidence": [],
    "word_meta": [],
    "training_log": []
  }
}
```

- Полный экспорт — `mode: "full"`, все четыре секции.
- Частичный — `mode: "partial"`, `sections` содержит только присутствующие.
- `sections` — карта присутствия (boolean), `counts` — длины массивов; отсутствующие секции опускаются в обеих картах.
- Экспорт читает все четыре store в одной readonly-транзакции (`DB.getSnapshot()`), иначе запись, закоммиченная между отдельными `await`, даёт torn snapshot с самосогласованными counts/checksum.
- `checksum` — SHA-256 канонического JSON `data` (`JSON.stringify` с сортировкой ключей). Если `crypto.subtle` недоступен — поле отсутствует, импорт предупреждает.
- `exportLogs` пишет `training_log` (и принимает legacy `logs` при импорте).
- После успешного экспорта — событие `EXPORT` с `exportId`, `mode`, `counts`, `checksum`, `result`.
- Старый формат (`version: alpha-v0.3`, `schemaVersion: 3`, без `data`) импортируется через адаптер: секции берутся с верхнего уровня.

## 7. Импорт

### 7.1 Поток
1. Выбор файла → чтение текста.
2. `JSON.parse` (ошибка → toast, БД не тронута, событие `IMPORT result:error` не пишется? — писать нечего, файл не принят; допустимо писать `IMPORT error` с причиной).
3. `validateImport(data)` → `{ errors, warnings }`.
4. `errors.length > 0` → показать первую/все ошибки, `return`, БД не тронута.
5. Показать сводку: режим, секции, количества, warnings (версия, схема, `tuning`, неизвестные ветки).
6. Пользователь выбирает:
   - **«Объединить»** (по умолчанию для частичного файла) — upsert присутствующих секций, отсутствующие не трогаются;
   - **«Заменить всё»** (только для полного файла или по явному выбору) — резервная копия → замена всех четырёх секций;
   - **«Отмена»**.
7. Запись одной транзакцией с явным `tx.abort()` на любой сбой.
8. Успех → событие `IMPORT` (`mode`, `counts`, `fileHash`, `backupId`, `result:ok`) → `loadNotes`/`render`/`renderTab` → toast.
9. Сбой → событие `IMPORT result:error` с причиной → toast; данные не изменены.

### 7.2 Правила валидации
Errors (импорт запрещён):
- не объект / массив;
- нет ни одной известной секции (`notes`, `word_evidence`, `word_meta`, `training_log`; legacy-алиас `logs` принимается как `training_log`);
- секция есть, но не массив;
- `notes[]`: нет `id`, `id` не непустая строка, дубль `id`, `text` пустой после `trim()`, `createdAt` не конечное число; `completedAt`/`reopenedAt`/`dueAt`/`deletedAt` — не `null` и не конечное число; `branchConfidence` присутствует и не конечное число (**F1**: строка `'0.9'` роняет `(…||0).toFixed(2)` и весь рендер);
- `word_evidence[]`: нет `stem`, `stem` пустой, нет `branch`, `branch` не строка (`null`/`undefined` → `DataError` в composite key); `evidence`/`distinctNotes` присутствуют и не числа;
- `word_meta[]`: нет `stem`, `stem` пустой;
- `training_log[]`: элемент не объект; `id` присутствует и не целое `>= 0`;
- `checksum` присутствует и не совпадает (формат 4).

Warnings (импорт возможен после подтверждения):
- `version`/`schemaVersion` не текущие;
- `tuning` присутствует — «настройки классификатора не применяются» (D2);
- неизвестный `branch` (кроме `''`) или `branchSource` (вне шести значений);
- `checksum` отсутствует;
- частичный файл (будет режим «объединить»);
- дубли `(stem, branch)` в `word_evidence` или дубли `stem` в `word_meta` — молча схлопнутся `put`; предупредить, что останется последняя запись;
- `dueConfidence`/`correctionCount`/`schemaVersion` заметки не числа — не блокирует, но фиксируется.

### 7.3 Семантика «Объединить»
- `notes`: upsert по `id`. Заметки, которых нет в файле, **остаются**.
- `word_evidence`: upsert по `['stem','branch']`; существующие записи не удаляются.
- `word_meta`: upsert по `stem`.
- `training_log`: добавить только события с новым `eventId`; дубликаты по `eventId` пропускаются.
- Никаких `clear()`.

### 7.4 Семантика «Заменить всё»
- Резервная копия текущего состояния в `backup`.
- Одна транзакция: `clear()` всех четырёх store → `put`/`add` всех записей из файла.
- Явное подтверждение: «Текущие заметки, обучение и логи будут удалены. Продолжить?».
- После успеха — `IMPORT mode:replace`, `backupId`.

### 7.5 Атомарность
- `DB.replaceAll` / `DB.mergeAll`: одна `readwrite`-транзакция по нужным store.
- Заполнение — синхронный цикл без `await`.
- **Эмпирически подтверждено** (Chrome 158 headless + CDP, ресерчер AUD-001):
  - async-ошибка запроса (`req.onerror`) всплывает и abort-ит транзакцию — данные целы;
  - синхронное исключение `put()` (`DataError` на невалидном ключе, `DataCloneError`) транзакцию **не** отменяет: она авто-коммитится, `clear()` и ранее поставленные `put()` применяются;
  - с явным `tx.abort()` в `catch` — полный откат.
- Поэтому `try { ... } catch (e) { tx.abort(); throw e; }` обязателен; без него DoD «нет частичного импорта» недостижим.
- `tx.abort()` вызывается синхронно, до любого `await`. После `await` транзакция может быть уже неактивна.
- `promTx` при падении не-последнего запроса реджектит `null` (`tx.error` ещё `null` в момент события `error`). Исправление: `reject(tx.error || req.error || new Error('Transaction failed'))`; в `catch` — `err?.message || err?.name || 'unknown error'`, а не `err.message`.
- Результат — `promTx(tx, tx.objectStore('notes').count())`; `0` — валидный результат осознанной очистки, не ошибка. Проверка `if (!result) throw` недопустима.
- `QuotaExceededError` по MDN — transaction failure (abort, откат), эмпирически не воспроизведён; считать `[UNVERIFIED]`.
- Логика вынесена в `www/js/idb.js` (`promTx`, `applyMergePlan`) и проверяется fake-транзакцией в `test/idb.test.js`: мутация удаления `tx.abort()` роняет тесты (`DataError`, `DataCloneError`), `{notes:[]}` резолвится `0`, `req.error` при `tx.error=null` даёт не-null `Error`. Реальный откат IndexedDB подтверждён эмпирикой ресерчера (S2/S3); интеграционный тест — TD-DEV-7.
- Исходные `id` логов при импорте **сохранять**, если это целое `>= 0` (`put`/`add` с явным id); иначе autoIncrement. Это сохраняет ссылки на события и не меняет журнал при round-trip.

### 7.6 Слияние обучения (`word_evidence`, `word_meta`)

Это отдельная семантика, потому что обучение — не список объектов, а счётчики. Здесь нельзя просто «добавить записи»: повторный импорт того же файла или импорт двух снимков одного устройства даст двойной счёт.

**Текущая модель:**
- `word_evidence` (ключ `['stem','branch']`): `evidence` — число коррекций, `distinctNotes` — число «разных заметок» (сейчас фактически тоже число коррекций — известный дефект M3), `lastSeenAt`.
- `word_meta` (ключ `stem`): `state` (`CANDIDATE|PROVISIONAL|CONFIRMED`), `distinctNotes`, `userCurated`.
- `recomputeMeta` выводит `state` из строк evidence: сумма, лучшая ветка, доля, пороги `CONFIRMED_MIN_*`, `PROVISIONAL_MIN_DISTINCT_NOTES`, `CONFLICT_RATIO_THRESHOLD`.

**Семантика «Объединить» (по умолчанию) — снимок против снимка:**
- Ключ строки — `['stem','branch']`; `branch: ''` — легитимный ключ («без ветки»), не «неизвестно».
- `evidence` = **max(текущее, импортируемое)**, не сумма. Экспорт — полный снимок, а не дельта; сумма двух снимков удвоила бы одни и те же коррекции.
- `distinctNotes` = **max(текущее, импортируемое)**.
- `lastSeenAt` = **max(текущее, импортируемое)**.
- Строки, которых нет в импорте, **остаются**.
- Строки, которых нет в текущей базе, **добавляются**.
- `word_meta` из файла **не принимается на веру**: `state` и `distinctNotes` пересчитываются `recomputeMeta` по объединённым evidence.
- **Tie-break при равном `evidence`** повторяет рантайм: строки сортируются по `branch` (возрастание), берётся последний максимум через `>` — как `getAll()` + `>` в `recomputeMeta`. Тест: `byt 5/1` + `rabota 5/3` → `PROVISIONAL`, `distinctNotes:3` (оба порядка входа). Импортированный `state` может быть устаревшим или относиться к другому набору evidence.
- `userCurated` = **логическое ИЛИ** (если пользователь отметил слово вручную хоть на одном устройстве, оно остаётся отмеченным). Слияние никогда не снимает `userCurated`.
- Если после слияния выросла конкурирующая ветка, `state` может понизиться (например, `CONFIRMED → PROVISIONAL`): это не потеря данных, а честный пересчёт при возросшем конфликте. Событие `IMPORT` фиксирует такие изменения в `details.learningStateChanges`.
- `word_meta` без evidence (сирота): `state` = `CANDIDATE`, `userCurated` — по ИЛИ; строка сохраняется, чтобы не терять ручную метку.

**Почему max, а не sum:**
- Экспорт — снимок состояния, не журнал дельт. При импорте снимка в базу, где уже есть часть тех же коррекций, сумма завышает уверенность и может ложно перевести слово в `CONFIRMED`.
- Max идемпотентен: повторный импорт того же файла не меняет counts. Это проверяется тестом.
- Цена: если два устройства накопили **разные** коррекции по одному и тому же ключу, max берёт большее, а не сумму — уверенность занижается. Это сознательный консервативный выбор до появления провенанса.

**Целевая модель (M3, отдельная карта):**
- `word_evidence` получает `noteCounts: { [noteId]: number }` или `corrections: [{eventId, noteId, ts}]`.
- `evidence` и `distinctNotes` становятся производными: `evidence = сумма коррекций`, `distinctNotes = число уникальных noteId`.
- Слияние становится **объединением множеств** по `eventId`/`noteId` — точным и идемпотентным, без компромисса max.
- Легаси-строки без провенанса переносятся как `legacyEvidence`/`legacyDistinctNotes`; при слиянии легаси-часть берётся по max, новая — по объединению. Это фиксируется в отчёте импорта как `legacy: true`.
- До M3 действует max-политика; после M3 — union. Формат экспорта 4 сразу содержит поля провенанса, если они есть, чтобы миграция была без потерь.

**Семантика «Заменить всё»:**
- `word_evidence` и `word_meta` полностью заменяются импортируемыми; `state` пересчитывается; `userCurated` берётся из файла.
- Это единственный режим, который удаляет текущее обучение; он требует двойного подтверждения и резервной копии (карта 002d).

**Частичный импорт только обучения:**
- Заметки не трогаются; слияние идёт по правилам выше; `word_meta` пересчитывается.
- Импорт `word_meta` без `word_evidence` не создаёт evidence; состояние остаётся `CANDIDATE` (или пересчитывается по текущему evidence).

**Наблюдаемость слияния (событие `IMPORT`):**
- `counts`: `{evidenceAdded, evidenceUpdated, evidenceUnchanged, metaRecomputed, stateChanged, userCuratedAdded}`.
- `details.learningStateChanges`: список `{stem, from, to, reason}`.
- `details.legacy`: сколько строк слито по max из-за отсутствия провенанса.
- `result: error` при любом сбое; данные не изменены.

**Тесты слияния:**
1. Импорт того же файла дважды → counts не меняются (идемпотентность).
2. Текущее 5/3, импорт 1/1 → 5/3; текущее 1/1, импорт 4/2 → 4/2.
3. `lastSeenAt` берётся максимальный.
4. Строка только в импорте → добавлена; только в текущей → осталась.
5. `branch: ''` сливается как обычный ключ.
6. `userCurated` ИЛИ: текущее `true`, импорт `false` → `true`; наоборот → `true`.
7. Импортированный `state: CONFIRMED` при слабом evidence → после пересчёта `CANDIDATE`/`PROVISIONAL`, не `CONFIRMED`.
8. Рост конкурирующей ветки → `state` понижается, `details.learningStateChanges` содержит запись.
9. «Заменить всё» → ровно импортируемые строки, ничего лишнего.
10. Легаси-строка без `noteCounts` + новая строка с провенансом → обе сохранены, легаси помечено.
11. Частичный импорт только `word_evidence` → заметки и логи не тронуты.

## 14. Решения пользователя (получены 2026-11-23)
1. **Подтверждение:** «Заменить всё» — двойной `confirm` с перечислением того, что будет удалено; «Полный сброс» — дополнительно ввод слова `СБРОС`. Обе операции создают резервную копию.
2. **Резервные копии:** хранить последние **3** снимка в IndexedDB; при переполнении удаляется самый старый.
3. **Частичный импорт заметок:** **upsert без удаления** — заметки из файла добавляются/обновляются по `id`, заметки вне файла остаются. Удаление — только через «Заменить всё» или восстановление копии.
4. **`checksum`:** включать в экспорт; при импорте отсутствие — warning, несовпадение — error. Решено оркестратором, не требует пользователя.
5. **Слияние обучения:** сейчас **max** по счётчикам (`evidence`, `distinctNotes`, `lastSeenAt`), `state` пересчитывается, `userCurated` — логическое ИЛИ. Точное объединение по `noteCounts`/`corrections` (noteId/eventId) — отдельной картой M3, не в этой карте.
