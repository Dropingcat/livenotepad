# Дизайн: гибридная фабрика разработки «Живой блокнот» (M2–M7)

Дата: 2026-11-23. Статус: черновик, ждёт одобрения. Код не писался.

## Цель

Довести приложение от M2 до M7 по `PROGRESS.md`, выполняя работу через субагентов и контролируя каждый модуль детерминированными гейтами. Фабрика должна быть честной: зафиксированные роли соответствуют реально запущенным агентам.

## Контекст (изучено в `E:\opencode_harness_portable`)

- Контроллер `scripts/code-factory/factory_ctl.py`: команды `init`, `submit`, `budget`, `auditor_block`, `finalize`, `status`, `replay`. Валидация контрактов в `contract_validator.py`, состояние в `state_reducer.py`.
- Схемы: worker — `module, code, description, written_by`; reviewer — плюс `verdict, comments[]` с `falsification` и `verified_by_commands`; tester — `result, passed, failed, coverage`.
- `written_by` проверяется как строка, равная типу роли (защита от подмены). Это формальная проверка, не доказательство личности агента.
- TD-184 (`config/tech_debt.json`, статус open): штатный вложенный диспатч специализированных агентов из харнесса не работает. Пока разрешён только явно объявленный `general`. Отчёты не должны выдавать `general` за специализированного агента.
- `submit worker` вызывает `_git_snapshot`: если git-репо нет, он делает `git init` и коммит в текущей директории. Проект сейчас не под git.
- В этой сессии доступны субагенты `general`, `explore`, `tribunal-judge`, `fact-checker`, `synthesizer`, `source-fetcher`, `claim-parser`, `article-writer`.

## Подход (выбран: гибрид C)

- Планирование: `writing-plans` по этому документу.
- Исполнение: субагенты `general` с ролевыми контрактами, скопированными из `agents/coder-worker.md`, `code-reviewer.md`, `code-tester.md`. Одиночные модули — последовательно, независимые — параллельно.
- Контроль: `factory_ctl.py` как детерминированный контроллер состояния и валидатор артефактов. Гейты — реальные команды (`npm test`, `node --check`, браузер).
- Арбитраж при расхождении ревьюера и воркера: после 2 раундов — `tribunal-judge` (процессный режим, без кода). После 3 раундов — эскалация пользователю.

## Модель данных фабрики

- Состояние: `OPENCODE_FACTORY_STATE=<проект>\.runs\factory_state.json`. Не `%TEMP%`.
- Один `init` на модуль, `task_id` = номер пункта из `PROGRESS.md` (например, `M2-AUD-001`).
- Артефакты: `<проект>\.runs\<task_id>\worker_<module>.json`, `reviewer_…json`, `tester_…json`.
- Журнал диспатча: `<проект>\.runs\dispatch_log.jsonl` с полями `task_id, role_contract, actual_subagent_type, session_id, started_at, result`. Здесь фиксируется реальный тип агента (`general`). Поле `written_by` в артефакте берётся из схемы роли, но не считается доказательством.

## Гейты (определены мной)

1. `npm test` — все тесты зелёные.
2. `node --check` для модуля, если он ES-модуль (извлечённый скрипт для `index.html`).
3. Для UI-изменений: браузерный смоук (консоль без ошибок, ключевой сценарий пройден, скриншот).
4. Ревьюер: каждый комментарий с `falsification`, scope явно указан.
5. Тестер: результат берётся из реального вывода команд, не из слов субагента.

## Ограничения и риски

- Субагенты `general` не дают специализированной изоляции ролей. Компенсация: отдельный контроллер, независимые гейты и журнал.
- Браузерные проверки требуют запущенного `npm run dev`.
- `_git_snapshot` может создать git-репо в проекте (см. вопросы ниже).

## Что решил я (проверьте)

- Гейты из раздела выше.
- Состояние и артефакты в `.runs\` внутри проекта.
- Журнал диспатча с реальным типом агента.
- Арбитраж через `tribunal-judge` после 2 раундов.
- Гранулярность: один `init` = один модуль `www/js/*` или один пункт из `PROGRESS.md`/аудита. `task_id` = `M2-AUD-001`, `M2-PR-<n>` (нумерацию PROGRESS вводим сейчас).
- Браузерный гейт выполняет основная сессия, а не субагент: доступность браузера у `general` не проверена. `package.json` содержит `dev` (`node scripts/serve.js`), так что `npm run dev` доступен.
- Спецификации M3–M7 пока нет: в `PROGRESS.md` только названия. Перед стартом каждого этапа пишу отдельный короткий дизайн и получаю одобрение.
